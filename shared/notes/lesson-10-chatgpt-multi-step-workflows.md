# Workflow vs Agent

## Traditional Workflow

A traditional workflow follows a predefined path.

Example:

Start
↓
Terraform Plan
↓
Terraform Apply
↓
Send Notification
↓
End

Characteristics:

* Fixed sequence
* No decision making
* Deterministic behavior

---

## Agent Workflow

An agent workflow dynamically chooses actions.

Example:

Goal
↓
Think
↓
Choose Action
↓
Execute
↓
Observe Result
↓
Choose Next Action
↓
Execute
↓
Complete

Characteristics:

* Dynamic behavior
* Decision making
* Adaptable execution path

---

# Planning

Planning is the process of converting a user goal into an executable workflow.

Example User Goal:

Generate Terraform for unmanaged resources

Generated Plan:

1. discover_resources
2. generate_terraform
3. create_pull_request

The plan acts as a roadmap for execution.

---

# Planner vs Executor

One of the most important architectural concepts introduced in this lesson.

## Planner

Responsibilities:

* Understand user goal
* Create execution plan
* Determine workflow sequence

Example:

User Goal
↓
Planner
↓
discover_resources
generate_terraform
create_pull_request

The planner decides what should happen.

---

## Executor

Responsibilities:

* Execute planned actions
* Call tools
* Update state
* Track progress

The executor decides how actions are performed.

---

# State

State is the workflow memory.

State stores:

* Tool outputs
* Intermediate results
* Workflow status
* Execution history
* Future inputs

Example:

```python
state = {
    "resources": [
        "vnet-prod",
        "storage-prod",
        "keyvault-prod"
    ]
}
```

State allows future tools to use information generated by previous tools.

---

# Workflow State Evolution

After Resource Discovery:

```python
state = {
    "resources": [
        "vnet-prod",
        "storage-prod"
    ]
}
```

After Terraform Generation:

```python
state = {
    "resources": [
        "vnet-prod",
        "storage-prod"
    ],
    "terraform": {
        "generated": True,
        "resource_count": 2
    }
}
```

After Pull Request Creation:

```python
state = {
    "resources": [...],
    "terraform": {...},
    "pull_request": {
        "pr_number": 123,
        "status": "created"
    }
}
```

The state gradually becomes the complete history of the workflow.

---

# Why State Is Important

Without State:

Tool 1
↓
Result Lost

Tool 2
↓
No Access To Previous Data

Workflow Breaks

With State:

Tool 1
↓
Store Result

Tool 2
↓
Read Result

Tool 3
↓
Read Previous Results

Workflow Continues Successfully

---

# Data vs Tool Names in State

Two possible designs were discussed.

Option 1:

```python
state["discover_resources"] = result
```

Option 2:

```python
state["resources"] = result
```

Preferred Approach:

```python
state["resources"] = result
```

Reason:

State should represent business data rather than tool names.

Tools are verbs.

State contains nouns.

Examples:

Tools:

* discover_resources
* generate_terraform
* create_pull_request

State:

* resources
* terraform
* pull_request

This creates a cleaner and more maintainable architecture.

# Conditional Branching

Workflows often need to change based on execution results.

Example:

discover_resources
↓
Resources Found?

Yes
↓
Continue Workflow

No
↓
Stop Workflow

This introduces decision points within the workflow.

---

# Error Handling

Tool Responsibilities:

* Detect errors
* Return structured error information

Example:

```python
{
    "success": False,
    "error": "Azure API unavailable"
}
```

State Responsibilities:

* Store errors
* Make errors available to future steps

Example:

```python
state["terraform"] = {
    "success": False,
    "error": "Azure API unavailable"
}
```

LLM Responsibilities:

* Explain failures
* Generate user-friendly responses

Example:

Terraform generation failed because the Azure API could not be reached.

# Shared State Architecture

Early Design:

```python
generate_terraform(resources)
```

Scalable Design:

```python
generate_terraform(state)
```

Advantages:

* Stable function interfaces
* Easier maintenance
* Simpler workflow expansion
* Supports large workflows

---

# Advantages of Shared State

Instead of:

```python
tool(
    resources,
    governance_rules,
    subscription_info
)
```

We can use:

```python
tool(state)
```

Benefits:

* Reduced complexity
* Easier scaling
* Cleaner architecture
* More reusable tools

---

# Risks of Shared State

Potential Problems:

* Large state objects
* Increased complexity
* Accidental state modification
* Harder debugging if unmanaged

Example:

```python
state["resources"] = None
```

This could unintentionally break downstream tools.

Enterprise solutions include:

* State validation
* State schemas
* Audit tracking
* Immutable state patterns

---

# Replanning

A workflow may need to change during execution.

Initial Plan:

1. discover_resources
2. generate_terraform
3. create_pull_request

Observed Result:

No resources discovered

Updated Plan:

1. notify_user
2. end_workflow

This process is called Replanning.

# Key Takeaways

1. Agents execute workflows, not just tools.
2. Planning and execution should be separate responsibilities.
3. State acts as workflow memory.
4. Shared state enables scalable architectures.
5. Conditional branching allows dynamic workflows.
6. Replanning enables adaptation to changing conditions.
7. Planner and Executor form the foundation of modern agent systems.
8. Multi-step workflows are the basis for enterprise Agentic AI solutions.
9. Most enterprise AI agents rely heavily on workflow state.
10. The architecture learned in this lesson directly supports building a Terraform Import and Drift Detection Agent.
